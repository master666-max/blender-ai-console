【生产系统"时间旅行"实战调研报告】

一、里程碑系统（均已核实一手来源）
1. rr（Mozilla，2011 起，开源）：只录非确定性输入（syscall 结果/信号/RDTSC），重放确定性重算。录制开销 1.2-1.4x（syscall 密集可达 4x）；用 seccomp-bpf 在被录进程内拦截 25 个高频 syscall，微基准提速 100x。强制定序单核串行换确定性。关联：你们"记录+重放"成本可以极低，前提是操作流本身可确定重算。
2. WinDbg TTD（Microsoft，2017）：软件仿真录全指令+内存，5-20x 减速、trace 每秒涨 5-50MB（每指令 1bit-1byte），索引文件再 1-2x trace 大小，可重放数百 GB。反面教材：全量记录的代价量级。
3. Undo UDB（商用，Linux）：2-5x 减速，只录非确定性数据，"99% 状态按需重建"；用 OS copy-on-write 存内存态，约 2x 进程内存。SAP HANA（500 万行 C++）生产在用。证明"录制最小区+惰性重建"是商用级路线。
4. GGPO（Tony Cannon，2006，2019 MIT 开源）：rollback netcode。网络上只传输入（每帧 5-20 字节），本地每帧存全量状态快照，预测错则回快照+重模拟若干帧（一帧 16.7ms 内完成）。前提：完全确定性模拟 + 便宜的快照保存/恢复。
5. Datomic（Cognitect，2012，现 Nubank，日 25 亿事务经 Jepsen 验证）：append-only 不可变 datom 日志，"更新"=新断言+旧 retraction；d/as-of 直接拿历史时刻的整个 db 值做查询——历史查询是一等公民而非事后重建。
6. Figma multiplayer（官方博客 2019）：非真 CRDT，服务器权威下简化为每 (对象ID, 属性) 一个 LWW 寄存器；对象 ID 由客户端生成 UUID 永不复用。

二、已解决的问题（可直接抄）
1. 录制开销压到近零的通用解：只记非确定性增量，确定性部分靠重算（rr/Undo/GGPO 同构）。→ 你们事件日志只需记"编译期非确定输入"（用户参数、上下文快照），节点求值结果可重算。
2. immer 的 patches+inversePatches：每个变更同时产出正/逆补丁，undo=applyPatches(inverse)；且补丁可重放到"略有不同的基树"上（官方文档明确支持 fork-replay 场景）。→ 这正是"增量逆补丁"最便宜的现成语义。
3. GGPO 的"回退不重推全部"：只重模拟从分叉点到现在的窗口，且重模拟是秒级内完成的常态操作而非异常路径。→ 意图层重推下游应被设计成"热路径"，你们 50ms 的重推已经符合这个门槛。
4. Figma 的引用稳定性：对象 ID 永久、客户端生成、删除不回收 ID，undo 靠 undo buffer 恢复对象及属性。
5. Git：content-addressed DAG，同一内容同一 hash，引用（指针）只是可变标签指向不可变对象——"回退"只是移动标签，对象永不失效。

三、坑/反直觉（有数字）
1. 记录方式决定数量级：同为逆向调试，GDB record full 实测慢 5 万-13 万倍（每条指令 ≥96 字节、仅存 20 万条且吃内存 ≥18GB），rr 1.2x，Undo 2-5x，WinDbg TTD 5-20x——差 4-5 个数量级，全在"录什么"。
2. PostgreSQL MVCC：多版本留在表内形成 dead tuple，VACUUM 回收但文件不缩小（VACUUM FULL 要全表排它锁重写）；MySQL InnoDB 反过来把旧版本放 undo log、主表紧凑但旧快照读要重构。两种 MVCC 都要付"清理"税——不可变/多版本永远伴随着回收机制。
3. rr 反直觉：单核串行是确定性的来源也是并行负载慢的来源；VM 里录制开销还会从 1.2x 涨到 1.4x。
4. GGPO：rollback 每"回退"实际是多次全模拟（每帧可能跑好几遍），CPU 换一致性；非确定性（浮点/随机）直接 desync。确定性是硬前提，不是优化项。
5. Figma 多人 undo 的坑：用户"undo 很多次→copy→redo 回到当前"，文档应不变但朴素实现会覆盖别人的后续编辑——他们让 undo 修改 redo 历史才解决。即：时间旅行必须和并发编辑的合并语义一起设计。

四、对本项目建议
(a) 事件日志+全量段落快照该不该改增量逆补丁？建议：不必全面改，改"分层混合"——保留段落级全量快照作 checkpoint（对应 GGPO 每帧快照/Datomic 索引段），在两个 checkpoint 之间用 immer 式 patches+inversePatches 记录细粒度变更（内存中段落状态本来就不大）。判据：单段参数改动频率高、且"段内回退"远多于"跨段回退"时才值得；若回退粒度总是整段，全量快照（0.6ms）已近零，逆补丁只省磁盘/内存不省定位时间。避免 Postgres 式"只增不清"：给日志加 compaction（Kafka log compaction 语义：按 key 保最新+定期 checkpoint 截断）。
(b) "回退后引用仍有效"（TNP 类问题）确有多个工业解：Git/Datomic 用内容寻址或不可变实体 ID，历史对象永不删除故引用恒有效；Figma 用永久 UUID+删除不回收；immer 用"补丁重放到不同基树"而非指针。推荐 Datomic 模式：把段落状态做成 append-only 的 (实体, 属性, 值, 事务t) datom 流，"回退到 t"只是换视图不是换对象，下游引用天然有效；重推仅负责重算派生值。
3. 学习 GGPO 把"回退+重推"当正常路径：确定性重放 + 廉价快照，比追求"永不重算"便宜。
4. 记录格式学 rr：只记会改变结果的东西（用户输入、随机种子、外部状态），其余可重算——你们的事件日志可大幅瘦身。
5. 时间旅行 UI 语义学 Figma：undo/redo 与"删层重推"必须是同一套历史模型，否则组合操作会出现"回到当前但文档变了"的诡异态。
