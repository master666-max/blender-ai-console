# Unreal / Unity / Godot 编辑器架构的 undo/程序化/变体机制

- 原始记录：`agent-9100ab6db06a410e.jsonl`

---

【d2-engine 调研报告】Unreal/Unity/Godot 编辑器架构的 undo/程序化/变体机制（均经 WebSearch 核实，源码路径已标注）

一、机制深读

1. Unreal Transaction Buffer（UTransBuffer）：撤销是「操作记录」不是「内容快照」。UTransBuffer 是内存态环形缓冲区（TransBuffer.h），MaxMemory 上限（UndoBufferSize 可配），存满丢最旧；仅记录哪些对象被改+足以反转的最小状态，靠 UObject::Modify() 在改前把属性序列化进 buffer，回撤后触发 PostEditUndo 让业务做恢复动作。与 Blender MemFile（整份 .blend 塞内存）的本质区别：粒度是「对象/属性 diff」而非全文件快照——所以 UE 能在 1GB 场景里做 O(修改量) 的 undo，Blender undo 是 O(文件大小)。另一个关键：FScopedTransaction 有 Cancel()（ScopedTransaction.h），且编辑中（如 gizmo 拖拽）事务保持 open，实时捕获属性变化，「编辑过程中撤」= 取消未完成事务+回滚已捕获部分。

2. Unreal Construction Script 的失效判定 = 「白名单属性 + 全量重建 + 状态抢救」。触发点：SpawnActor、PostEditMove、PostEditChangeProperty（ActorConstruction.cpp）。失效判定极粗——任何属性变更都 RerunConstructionScripts，没有细粒度依赖分析；但它用两招兜住：① 销毁前把实例属性序列化到持久 buffer，重建后回灌（components 的实例状态走 UActorComponent::GetComponentInstanceData() 抢救，论坛核实：引擎「handles saving and reapplying changes you made to the newly created component」，但 Instanced 子对象是已知洞）；② 文档原话「destroying all autogenerated components; will attempt to preserve the root component location」——明确区分「生成的组件（可销毁）」与「用户加的组件（不可动）」。这跟我们 GN「改参数→重算」同构，但 UE 把「谁可以删」编码进了所有权，而不是靠 diff。

3. Unity Prefab Variant = 显式序列化的 override 表（和 USD opinion 栈几乎同构）。.prefab YAML 里 variant 就是一个 PrefabInstance（class ID 1001）：m_SourcePrefab 指向基座 guid，m_Modifications 数组存 diff（target fileID + propertyPath 点分路径 + value 字符串），外加 m_AddedGameObjects/m_RemovedGameObjects/m_AddedComponents/m_RemovedComponents（Unity 官方 YAML 文档）。改基座后 Variant 的「同步」不是同步——变体只存 patch，未覆盖的属性每次加载时从基座 live 解析，传播是默认态，零成本。冲突裁决：离最终对象最近的赢（scene instance > outer prefab > variant > base）。

4. Unity override 的脆弱点（对我们最有价值）：override 按 fileID+propertyPath 定位，基座重命名/改类型/删组件会让 override 静默失效（加载时直接丢弃不报错）。社区实践是用 PrefabUtility.GetPropertyModifications 扫 dangling override 做成 CI 步骤（bugnet.io 方案）。

5. Godot Resource：不是内容寻址，是路径寻址 + 场景内唯一 ID。全局 ResourceLoader 缓存以路径为 key；内嵌资源用 resource_scene_unique_id（保存时自动生成，同 ID 冲突只有层级最早的保留）。Godot 没有 Prefab Variant 的显式 override 表，等效物是「instancing + editable children」和 resource_local_to_scene（instantiate 时对资源做 duplicate，让实例改动不回写共享资源）。

6. 分帧/异步重算：UE5 PCG 框架是标杆——① 空间分块：Volume 切成 partition cell，参数变化只标脏受影响 Cell，脏 Cell 重跑图、其余用缓存（Epic Productboard 5.6 确认：图执行多线程默认开启、逐 Data CRC 缓存默认开启）；② 帧预算：pcg.EditorFrameTime / pcg.FrameTime 毫秒级预算调度，运行时限并发 pcg.RuntimeGeneration.NumGeneratingComponents；③ 失效靠依赖图：读全局状态（GameplayTag、Time.Now、全局单例）会静默毁掉增量更新。Unity 侧无框架级方案，标准做法是 Jobs+Burst 算数据、主线程只在最后一帧 SetVertices/SetIndices（TTG 博客核实：重计算全在池化线程，Mesh 实例化延迟到「绝对必要」才做）。

7. 「程序化重跑不覆盖手改」——引擎的答案高度一致：分所有权。Unity：手改=override 表条目，程序化改的是基座，两者天然不相交；手改想进基座必须显式 Apply。Houdini Engine：cooked 输出归 HDA actor 所有，用户想要手改必须显式 Bake 成独立资产（Bake 后与 HDA 断开连接，SideFX 官方文档）——「要覆盖请先声明」。Unreal：重建只动 autogenerated components。

二、设计转译（我们的 X → Y）

1. undo：MemFile 全量快照 → 按「opinion 条目+被改对象」记录最小 diff，只对 op 编译产物做反向 patch；至少 AI 重推产生的改动要走事务 API，与用户手改同层可撤。
2. modifier 栈序恢复：学 RerunConstructionScripts 的所有权标注——AI 生成的 modifier 打「autogenerated」标记（如存 custom property），重编译时「销毁+重插标记项、保留未标记项原索引」，而不是事后恢复索引。
3. 变体/覆盖：AI 计划和用户手改分两张表——AI 写「计划层」（可整层替换），用户编辑落「override 表」（fileID/路径寻址的 propertyPath 级 diff），求值顺序 base→AI→user override，人永远赢。
4. 失效判定：不要学 UE 的「任何属性变都全量重算」，要学 PCG 的依赖图+分块标脏；GN 节点组按子树切「重算 cell」，参数变化只重算下游。
5. GN 卡顿：学 PCG 帧预算——把 GN 求值放进带毫秒预算的调度器，超预算留给下一帧；大网格学 Unity「后台算纯数据，最后一步才回主线程建 mesh」。
6. override 稳定性：学 Unity 的教训——用稳定 ID（GN 节点的稳定命名）而非列表索引定位 override，并做 CI 级「悬空 override」扫描。

三、反直觉/打脸

1. Unity 的变体「同步」根本不存在：传播是加载时 live 解析的副作用，不是维护步骤。我们不需要写「AI 重推后同步」逻辑，只需要让产物层不持有非 override 值。
2. UE 的失效判定出奇地粗（任何属性变更全量重建），它靠「状态抢救 buffer」兜底而不是靠精确依赖分析——粗粒度失效+可靠恢复 ≈ 细粒度失效的工程性价比可能更高。
3. UE undo 是内存态、保存地图即清空、重启全丢——引擎界都不认为 undo 该持久，持久历史是 journal/版本控制的职责。别在 undo 上过度设计持久化。
4. 最成熟的「程序化 vs 手改」方案（Houdini Engine）没有做任何自动保护：它直接要求用户 Bake 出断连副本——有时候「复制一份让你随便改」比复杂的合并策略更好用。

四、可直接抄的策略

1. 属性级 override 表格式：抄 Unity m_Modifications 四元组 {目标ID, propertyPath(点分), value, objectReference}（docs.unity.com YAML prefab serialization）——可直接做我们的用户手改存储格式。
2. 重建状态抢救：抄 AActor::RerunConstructionScripts 流程（/Engine/Source/Runtime/Engine/Private/ActorConstruction.cpp）——销毁前序列化实例属性→重建→回灌，配合 UActorComponent::GetComponentInstanceData() 的组件级方案。
3. 空间分块增量：抄 PCG partition cell + per-Cell 缓存 + 依赖图标脏（Epic roadmap「Execution Efficiency」条目），以及「图必须空间局部化、禁止节点读全局状态」的架构铁律。
4. 帧预算调度：抄 pcg.EditorFrameTime/pcg.FrameTime 的 CVar 预算模式。
5. 事务取消：抄 FScopedTransaction::Cancel()（UnrealEd/Public/ScopedTransaction.h）支持「编辑中撤」。
